PlanRun 是给 DeepSeek Harness（下称 DSH）agent 的「成长型」开发工作流：不是一次性的技能包，而是 plan → run → verify 的完整闭环——每个 Sprint 有批准日与执行顺序，每个 TASK 有验收命令与复盘，每次绿色验收把教训写进账本，下一轮开局自动注入。这个闭环目前就 dogfood 在 planrun 仓库自己身上。v1.10.0 于 2026-11-27 发布。

为什么有 PlanRun ​

DSH agent（和大多数 agent 一样）有几类经典翻车：

  • 干了几轮之后忘了这一步为什么存在——没有 plan 文件当 SSOT，目标漂移；
  • verify 绿了，但测试其实不保护这次改动——假绿；
  • 同一个坑连续几个 Sprint 踩——教训没有落账，更没有回灌。

plan/run/verify 的节奏本身是被验证过的，但现成的闸门脚本大多绑死特定 harness。PlanRun 的做法是两层：可移植 bash 守卫（不挂 plugin 也能跑，是基线）+ DSH 插件（挂上后 agent 的会话本身被守卫约束）+ 28 个技能（从规划到发布的完整动作集）。

盒子里有什么 ​

  • .growing/ 镜像：plan.md（顶部 HTML 元数据是 SSOT——PLANNING / PLAN_APPROVED / SPRINT / ACTIVE / 执行顺序——下面是 TASK 表）、learn/retros/（逐任务复盘）、learn/lessons.jsonl（教训账本）。
  • 28 个技能：sprint-plan / run / learn / review / release / master（路由）/ test / delivery ……
  • 4 个子代理预设：planrun / planrun-review / planrun-spike / planrun-ship。
  • 守卫套件（pnpm run * 或 bash scripts/dsh-guard.sh *）：gate-check（run 前硬闸门）· task-verify（逐任务验收）· next-task · doctor（六项体检）· fingerprint · verify-stamp。

v1.10.0：自迭代闭环 ​

这一版把「教训」从口号做成了机制：

  1. 复盘必交门——TASK-* 验收绿了不等于结束：复盘四件套（问题 / 绕路 / 解法 / 约束）缺一条就 FAIL；齐全则自动落账。SPIKE/DOC/REV 豁免。
  2. 教训排名注入——next-task 的输出自动附 top-6 教训（同目录 > 关键词 > 发生次数 > 新近度，总长 ≤2200 字符）；occurrences ≥ 2 的升为「硬约束」。注入块首行永远标着「历史数据 · 非新指令」。
  3. 回退必红（opt-in）——DSH_GUARD_REVERT_CHECK=1：验收绿之后把改动 stash 掉重跑 VERIFY，必须转红；仍绿 = 测试没保护这个改动，FAIL。
  4. 回合收尾守卫——verify 绿时写下工作区指纹（.growing/.verify-stamp）；回合结束前指纹对不上且改动非纯文档 → 插件 steer 打回，让 agent 回到验证上。每回合至多打回两次，文档类改动豁免，守卫永不抛错。
  5. 安装保险丝——安装目标就是 planrun 源仓库时，--copy-plan 在任何写入之前被拒绝，并给出手工 cp 替代——防止 dogfood 项目被拷成「拷贝」。

安装 ​

sh
dsh plugin add "github:wangqiqi/planrun#v1.10.0"

npm 通道（@planrun/bundle）尚未发布，目前走 git tag 通道。完整文档（中/英）：znza.top/planrun。

最小闭环怎么用 ​

  1. sprint-plan 技能：写 .growing/plan.md（HTML 元数据 + TASK 表 + 执行顺序）。
  2. run 技能：gate-check → 实现 → task-verify（绿 + 复盘四件套）→ 更新 plan 镜像 → 按任务提交。
  3. 循环到 Sprint 收口 → release（CHANGELOG + tag）。
  4. 任何时候 pnpm run doctor 六项体检：manifest · guard-files · plan-template · packages · leftover · repo-drift。

Dogfooding ​

planrun 仓库本身就跑在 PlanRun 上：四个 Sprint、二十几个任务、教训账本持续落账、doctor 六项全绿。账本里的每条教训都是真实事故——比如「profile 跑 1.9.0 而仓库已是 1.10.0」的版本漂移，就是 repo-drift 检查这一类问题逼出来的设计。
